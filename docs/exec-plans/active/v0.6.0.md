# Execution Plan: v0.6.0 — Atomic delivery persistence and Kafka commit safety

> **Status:** Active
> **Started:** 2026-06-12
> **Target:** Prevent Kafka offsets from being committed unless the delivery outcome and attempt history are durably persisted.
> **Depends on:** completed v0.4.0 validation-pipeline hardening
> **Followed by:** queued v0.7.0 retry claim leases

## Goal

Make delivery-result persistence a single success-or-failure operation and propagate
database failures to the Kafka consumer so the system preserves explicit at-least-once
processing semantics.

## Documentation authority

- `docs/spec.md` is the living product and behavior contract and must describe the final behavior.
- ADRs record why architectural choices were made and are superseded rather than silently rewritten.
- `docs/architecture.md` maps the current implemented structure and data flow.
- This exec plan is the temporary implementation and verification contract for this increment.
- `PROGRESS.md` records only mechanically verified state after implementation.

## Acceptance criteria

- [x] Event state and all attempts produced by one processed batch are persisted in one PostgreSQL transaction.
- [x] A failed transaction leaves neither partial state transitions nor partial attempt history.
- [x] Kafka messages are committed only after required delivery-result persistence succeeds.
- [x] A persistence failure leaves Kafka messages uncommitted so they can be redelivered.
- [ ] Duplicate Kafka delivery does not create duplicate event rows or lose state; duplicate webhook calls remain an explicit at-least-once possibility.
- [ ] Attempt history records every HTTP call actually performed; this increment does not claim exactly-once or deduplicated delivery attempts.
- [x] Retry-poller persistence failures are returned and logged as batch failures rather than reported as successful outcomes.
- [x] Existing happy-path and retry behavior remains unchanged.
- [x] Lint, build, layered tests, and E2E smoke tests pass.

## Phase 1: Specify the persistence contract

### Step 1: Add failing contract tests

- [x] Add Kafka consumer tests proving successful persistence permits commit and persistence failure prevents commit.
- [x] Add handler tests proving outcome-persistence errors are returned to callers.
- [x] Add PostgreSQL integration tests proving event state and attempt inserts commit or roll back together.
- [x] Cover both Kafka-originated events and retry-polled events.
- **Verify:** focused tests fail for the intended missing behavior before production changes.

### Step 2: Define one outcome persistence boundary

- [x] Introduce repository input types representing an event outcome and its delivery attempts without exposing pgx details.
- [x] Add repository operations for atomically creating Kafka-originated outcomes and updating retry-originated outcomes.
- [x] Keep the two persistence semantics explicit: initial Kafka delivery creates the event record; retry delivery updates an existing record.
- [x] Return errors with operation context; do not log-and-continue inside the repository.
- **Verify:** repository integration tests pass against Testcontainers PostgreSQL.

## Phase 2: Propagate failures through delivery processing

### Step 3: Make delivery processing return persistence errors

- [x] Change the delivery-handler contract so `ProcessBatch` and `ProcessEvents` return categorized outcomes plus an error.
- [x] Persist state and attempt history through the new atomic repository operations.
- [x] Return persistence failures without presenting the batch as durably completed.
- [x] Keep webhook outcome computation separate from persistence semantics.
- **Verify:** handler unit tests cover successful persistence, rollback, and error propagation.

### Step 4: Gate Kafka commits on durable persistence

- [x] Update the consumer to commit a fetched batch only when `ProcessBatch` returns nil error.
- [x] Leave all messages in the failed batch uncommitted; accept batch redelivery as the at-least-once tradeoff.
- [x] Log the persistence failure with batch size and Kafka partition/offset context available from the fetched messages.
- [x] Preserve current behavior for malformed messages, which are committed separately to avoid poison-message blocking.
- **Verify:** fake-reader tests prove commit/no-commit behavior and remain race-clean.

### Step 5: Propagate retry-poller processing failures

- [x] Change `EventProcessor.ProcessEvents` to return an error.
- [x] Ensure the poller logs a failed retry batch distinctly from delivered/retrying/failed outcome counts.
- [x] Do not add lease recovery in this increment; claimed rows may remain `processing` until v0.7.0.
- **Verify:** poller tests cover processor error reporting and graceful shutdown.

## Phase 3: System verification and documentation

### Step 6: Validate redelivery and atomicity

- [ ] Add an E2E or integration-level fault-injection scenario where persistence fails before Kafka commit and the message is processed again after recovery.
- [ ] Verify attempt history and event state never expose a partial committed outcome.
- [ ] Verify duplicate processing does not create duplicate event rows and that every repeated HTTP call remains visible in attempt history.
- **Verify:** targeted Kafka, PostgreSQL, and app suites pass repeatedly.

### Step 7: Update durable documentation

- [ ] Correct `docs/spec.md` so it describes the actual Kafka-first ingestion flow and the durable-persistence-before-commit invariant.

- [ ] Update `README.md`, `docs/LIMITATIONS.md`, and `docs/next-steps.md` only where behavior or roadmap statements changed.
