# Execution Plan: v0.7.0 — Retry claim leases and crash recovery

> **Status:** Active
> **Started:** 2026-06-12
> **Target:** Recover abandoned retry claims safely without allowing stale workers to overwrite newer outcomes.
> **Depends on:** v0.6.0 atomic delivery persistence and Kafka commit safety
> **Followed by:** queued v0.8.0 poller throughput and observability

## Goal

Replace permanent `processing` claims with expiring, owner-fenced leases so retry
events survive worker crashes while retaining at-least-once delivery semantics.

## Acceptance criteria

- [ ] Every retry claim records an owner and expiration deadline atomically with the transition to `processing`.
- [ ] Expired `processing` events become claimable again without manual database intervention.
- [ ] A stale worker cannot persist an outcome after another worker has reclaimed the event.
- [ ] Successful, retrying, throttled, and failed outcomes clear lease metadata atomically with state persistence.
- [ ] Concurrent workers do not hold valid claims for the same event simultaneously.
- [ ] Schema migration is backward-safe for existing rows and reversible through its down migration.
- [ ] Lint, build, integration tests, and E2E crash-recovery coverage pass.

## Phase 1: Define and migrate the lease model

### Step 1: Record the architecture decision

- [ ] Add or supersede an ADR defining PostgreSQL polling as the retry scheduler and expiring owner-fenced claims as its crash-recovery mechanism.
- [ ] Define the lease duration default, ownership identity, expiration behavior, and at-least-once duplicate-delivery tradeoff.
- [ ] Keep PostgreSQL as the only durable retry schedule; do not add Redis or Kafka retry topics.
- **Verify:** ADR agrees with the living spec and existing Kafka/PostgreSQL responsibility split.

### Step 2: Add lease state to persistence and domain models

- [ ] Add nullable `processing_owner` and `processing_deadline` columns plus an index supporting expired-lease lookup.
- [ ] Extend the event persistence model and scans to carry lease metadata where required.
- [ ] Configure a worker lease duration with a documented default longer than the maximum normal delivery timeout for one claimed batch.
- [ ] Use the existing worker `InstanceID` as the claim owner.
- **Verify:** migration up/down tests and configuration tests pass.

## Phase 2: Implement owner-fenced claiming

### Step 3: Replace pending fetch with an explicit claim operation

- [ ] Rename the repository operation to express claiming rather than reading.
- [ ] Atomically claim due `retrying`/`throttled` events and expired `processing` events using `FOR UPDATE SKIP LOCKED`.
- [ ] Set `status=processing`, owner, and deadline in the same statement.
- [ ] Return whether each event was newly due or reclaimed for observability.
- **Verify:** PostgreSQL integration tests cover eligibility, limits, owner fields, and future deadlines.

### Step 4: Fence outcome persistence by lease owner

- [ ] Require retry-originated outcome persistence to match event ID, `status=processing`, and `processing_owner`.
- [ ] Treat zero updated rows as a lost/stale claim, not as successful persistence.
- [ ] Clear lease fields in the same transaction that writes the outcome and attempts.
- [ ] Ensure an expired first worker cannot overwrite a second worker's committed result.
- **Verify:** concurrent repository tests exercise reclaim and stale-owner rejection deterministically.

## Phase 3: Crash recovery behavior

### Step 5: Wire worker identity and lease configuration

- [ ] Pass `InstanceID` and lease duration from worker configuration into the retry poller claim operation.
- [ ] Log claim owner, lease deadline, and reclaimed count without high-cardinality event labels in metrics.
- [ ] Preserve graceful shutdown; do not release claims by resetting rows during shutdown because in-flight HTTP outcomes may be uncertain.
- **Verify:** worker bootstrap and poller unit tests pass.

### Step 6: Add crash and expiration scenarios

- [ ] Prove a claimed event is unavailable to a second worker before expiration.
- [ ] Prove it becomes claimable after expiration.
- [ ] Prove the stale first owner cannot commit after reclamation.
- [ ] Add a thin E2E recovery scenario that abandons a claim and reaches a valid final state after lease expiry.
- **Verify:** integration and E2E suites pass repeatedly without arbitrary long sleeps.

### Step 7: Update durable documentation

- [ ] Update the living spec state machine with lease acquisition, expiration, and reclaim behavior.
- [ ] Update architecture diagrams and database schema documentation.
- [ ] Update limitations and operational guidance for duplicate delivery after lease expiry.
- [ ] Add a learning note about leases, fencing tokens/owners, and why timeout alone is insufficient.
- **Verify:** docs consistently distinguish row locking from a durable processing lease.
