# Execution Plan: v0.9.0 - Rate-Control Contract Normalization

> **Status:** Queued
> **Target:** Separate rate, burst, and concurrency controls and make throttling behavior algorithm-independent.
> **Depends on:** v0.8.0 retry poller throughput and observability
> **Followed by:** queued v0.10.0 per-subscription delivery persistence

## Goal

Remove the current ambiguity where one `rate_limit` value is interpreted as both requests per
second and maximum concurrent requests, while Redis and fallback paths enforce different traffic
contracts. Establish one explicit policy model before changing the distributed algorithm.

This increment intentionally keeps the Redis sliding-window log. It changes the contract around
the limiter, not the limiter algorithm itself. Token bucket is deferred to a spike and is not a
v1 requirement unless measurements prove the normalized implementation insufficient.

## Current debt being addressed

- Redis always enforces the fixed `DefaultRateLimit = 100` and ignores `Subscription.RateLimit`.
- The in-memory fallback uses token bucket semantics with a burst of 10, unlike the Redis path.
- `Subscription.RateLimit` is also used as local semaphore capacity even though rate and concurrency are different dimensions.
- A rate-limiter rejection becomes a generic retry outcome instead of the domain's `throttled` state.
- The limiter only returns allow/deny, so retry scheduling cannot use an algorithm-provided availability delay.
- Redis failure silently changes a global distributed limit into independent per-process limits.

## Acceptance criteria

- [ ] Subscription policy represents sustained requests per second, burst capacity, and concurrency limit independently.
- [ ] Existing subscriptions migrate to documented backward-compatible defaults.
- [ ] Rate limiter decisions receive the subscription policy instead of using a fixed global constant.
- [ ] Rate limiter decisions can return a retry delay without exposing Redis or a specific algorithm to delivery code.
- [ ] Semaphore capacity uses only the concurrency setting, never the rate setting.
- [ ] Rate-limit and concurrency rejection persist `throttled` without incrementing delivery attempts.
- [ ] Redis degradation behavior is explicit in logs, metrics, documentation, and tests.
- [ ] API, PostgreSQL, worker, unit, integration, and E2E validation pass without changing the Redis sliding-window algorithm.

## Phase 1: Define the control model

### Step 1: Record the contract decision

- [ ] Add an ADR separating sustained rate, burst capacity, and in-flight concurrency.
- [ ] Define units and defaults: requests/second, maximum immediate burst, and simultaneous HTTP calls.
- [ ] Define whether zero values mean invalid, disabled, or defaulted; avoid implicit mixed meanings.
- [ ] Define rate-limited and concurrency-limited outcomes as internal throttling, not delivery failure.
- [ ] Define Redis outage behavior as degraded local enforcement, including the loss of a global limit.
- **Verify:** ADR, living spec, and API contract use the same terminology.

### Step 2: Add schema and domain policy fields

- [ ] Preserve `rate_limit` as requests per second for API compatibility.
- [ ] Add `burst_size` and `concurrency_limit` columns with explicit defaults and constraints.
- [ ] Extend domain, repository scans, API serialization, and subscription validation.
- [ ] Add reversible migrations that map existing rows to behavior-preserving defaults where possible.
- [ ] Document that the old code used `rate_limit` as concurrency; choose and record the migration default rather than silently preserving that coupling.
- **Verify:** migration up/down tests and subscription repository/API tests pass.

## Phase 2: Make delivery algorithm-independent

### Step 3: Replace boolean limiter decisions with a policy contract

- [ ] Introduce a rate policy value object containing rate and burst.
- [ ] Replace `Allow(ctx, subscriptionID) (bool, error)` with a decision that includes allowed state, retry delay, and degraded-mode metadata where useful.
- [ ] Pass the matching subscription policy into every decision; remove `DefaultRateLimit` from runtime Redis enforcement.
- [ ] Keep algorithm details inside `internal/resilience`.
- [ ] Ensure policy changes take effect without requiring a process restart or stale per-subscription cache replacement.
- **Verify:** contract tests run against both Redis sliding-window and in-memory implementations.

### Step 4: Separate concurrency from rate

- [ ] Build local semaphore capacity from `ConcurrencyLimit` only.
- [ ] Extend the distributed semaphore API/configuration if per-subscription concurrency is not currently honored.
- [ ] Prove rate changes do not alter simultaneous request count and concurrency changes do not alter requests/second.
- [ ] Preserve cross-worker concurrency coordination when Redis is available.
- **Verify:** focused handler and resilience tests exercise independent rate and concurrency values.

### Step 5: Persist throttling explicitly

- [ ] Add an explicit throttled delivery outcome distinct from retryable HTTP failure.
- [ ] Persist rate-limit, circuit-open, and semaphore-full outcomes as `throttled`.
- [ ] Do not increment attempts when no HTTP request occurred.
- [ ] Schedule the next attempt using limiter-provided delay where available, with a bounded fallback policy.
- [ ] Define fan-out aggregation when one subscription succeeds and another is throttled or fails.
- **Verify:** handler, repository, retry-poller, and E2E tests cover state and attempt-count invariants.

## Phase 3: Degradation and operational clarity

### Step 6: Make Redis fallback observable

- [ ] Emit a dedicated counter/gauge for rate-limiter degraded mode and fallback decisions.
- [ ] Log transitions into and out of degraded mode without logging every request repeatedly.
- [ ] Document that local fallback can exceed the configured global rate by approximately the number of active workers.
- [ ] Decide whether operators can configure fail-closed behavior for strict receiver contracts; do not add it unless justified and tested.
- **Verify:** Redis outage tests prove selected behavior and metrics without requiring host-local Redis.

### Step 7: Update durable and local documentation

- [ ] Update spec, architecture, README, limitations, ADR 004/011 references, and package READMEs.
- [ ] Add a learning note explaining rate versus burst versus concurrency and why one field cannot safely represent all three.
- [ ] Keep token bucket described as an optional spike; do not claim it is required or implemented in this increment.
- **Verify:** documentation consistently states that Redis still uses sliding-window log after v0.9.0.

## Closure

- [ ] Lint, build, race-gated tests, PostgreSQL/Redis integration, E2E, and configuration compatibility tests pass.
- [ ] `PROGRESS.md` records the normalized policy contract and remaining sliding-window limitations.
- [ ] Move this file to `done/`; promote v0.10.0 per-subscription delivery persistence from `queued/` to `active/`.
