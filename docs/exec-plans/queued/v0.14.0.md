# Execution Plan: v0.14.0 Minimal Operational Readiness

> **Status:** Queued for review
> **Estimated effort:** 1-2 focused engineering sessions
> **Depends on:** Operational dependency readiness
> **Release criterion:** Demonstrate that a reviewer can install, validate, inspect, and roughly size
> Dispatch without a production-operations program.

## Goal

Give Dispatch a small but credible operational finish for v1.

This increment should make the system easy to run and inspect, document the most important failure
modes, and record a bounded capacity baseline. It should not attempt to simulate a full production
operations program for a portfolio project.

## Accepted Contract

- V0.14 is minimal operational readiness, not full production certification.
- The main validation path should be easy to run from the repository.
- Documentation should be short, practical, and linked from README.
- Capacity evidence must name the environment and methodology; it must not become a universal SLO.
- PostgreSQL, Kafka, and Redis failure behavior should be explained at operator level.
- Backup/restore, rollback drills, full alerting, and exhaustive outage simulations are deferred
  unless a missing piece blocks the simple validation path.

## Non-goals

- No new product features.
- No API contract hardening.
- No package-boundary refactor such as extracting `internal/delivery` from `internal/kafka`.
- No cloud-provider-specific deployment.
- No full backup/restore automation.
- No migration rollback exercise beyond documenting the current boundary.
- No Prometheus alert-rule suite unless it is a tiny docs-only mapping to existing metrics.
- No large capacity envelope or production SLO claim.

## Phase 1: Inventory And Scope Cut

- [ ] Inventory current commands, scripts, Compose files, Kubernetes manifests, dashboards, and
  performance harnesses.
- [ ] Identify the shortest useful validation path for a reviewer.
- [ ] Confirm what v0.14 intentionally defers:
  - full backup/restore automation;
  - migration rollback drills;
  - complete alert-rule implementation;
  - full outage simulation matrix.
- **Verify:** the plan progress log records the scoped-down v0.14 decision.

## Phase 2: One-Command Validation Entry Point

- [ ] Review `make validate-basic` and the underlying performance-validation smoke mode.
- [ ] Keep or improve the command so it validates:
  - clean Compose setup;
  - migrations;
  - API readiness;
  - worker delivery;
  - PostgreSQL correctness assertions;
  - evidence capture and cleanup.
- [ ] Add a short README path for reviewers: prerequisites, command, expected result, cleanup.
- **Verify:** `make validate-basic` runs successfully or the blocker is documented with exact local
  remediation.

## Phase 3: Minimal Operational Guide

- [ ] Add one concise operational guide, or tighten an existing guide, covering:
  - how to start the local stack;
  - how to seed normal and retry flows;
  - how to inspect API, receiver, Prometheus, and Grafana;
  - how `/health` and `/ready` behave;
  - how to stop and clean up.
- [ ] Link it from README.
- [ ] Avoid duplicating behavior already owned by `docs/spec.md`.
- **Verify:** the guide gives a reviewer enough context to run the project without reading every
  historical exec plan.

## Phase 4: Basic Failure-Mode Notes

- [ ] Document the three most important dependency failures:
  - PostgreSQL unavailable;
  - Kafka unavailable;
  - Redis unavailable.
- [ ] For each failure, explain:
  - expected API/worker readiness behavior;
  - expected delivery behavior;
  - metrics/logs to inspect;
  - recovery expectation.
- [ ] Keep worker interruption and at-least-once duplicates referenced through existing reliability
  docs instead of writing a large incident manual.
- **Verify:** failure notes reference actual endpoints, metrics, and existing behavior.

## Phase 5: Small Capacity Baseline

- [ ] Run `make perf-smoke`, or an equivalent smaller command if local resources are constrained.
- [ ] Optionally run `make perf-baseline` if the environment can support it without turning this into
  a large benchmarking increment.
- [ ] Record:
  - date;
  - machine/runtime context;
  - command;
  - event count and retry count;
  - observed throughput;
  - what the result does not prove.
- [ ] Update `docs/PERFORMANCE.md` or add a short v0.14 capacity note linked from it.
- **Verify:** capacity guidance is reproducible and bounded to the measured environment.

## Phase 6: Documentation Reconciliation

- [ ] Update README with only high-level operational entry points.
- [ ] Update `docs/LIMITATIONS.md` to reflect what v0.14 intentionally leaves manual or deferred.
- [ ] Update Kubernetes docs only if probe or deployment guidance changed.
- [ ] Update `PROGRESS.md` with final validation evidence and make v1.0.0 release hardening the next
  planning step.
- [ ] Move this exec plan to `done/`.
- **Verify:** docs do not duplicate long operational procedures across multiple files.
