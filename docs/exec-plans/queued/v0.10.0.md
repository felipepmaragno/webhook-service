# Execution Plan: v0.10.0 - Distributed Token Bucket Rate Limiting

> **Status:** Queued
> **Target:** Replace the Redis sliding-window log with a constant-state distributed token bucket while preserving the normalized v0.9.0 policy contract.
> **Depends on:** v0.9.0 rate-control contract normalization

## Goal

Adopt one rate-limiting model for Redis and in-memory fallback: sustained refill rate plus
explicit burst capacity. Reduce Redis storage and per-request sorted-set work while retaining
atomic cross-worker enforcement and predictable receiver protection.

## Why token bucket

- Webhook traffic is naturally bursty and receivers commonly express capacity as rate plus burst.
- State is constant per subscription rather than one sorted-set member per accepted request.
- Redis and in-memory paths can share the same externally visible policy.
- Burst capacity becomes explicit instead of implicitly allowing up to one full sliding-window limit.

Token bucket does not guarantee a strict maximum in every rolling one-second interval. That semantic
change must be accepted and documented rather than presented as an implementation detail.

## Acceptance criteria

- [ ] Redis and in-memory paths enforce the same rate and burst policy within documented distributed/fallback limits.
- [ ] Redis stores constant-size state per active subscription.
- [ ] Token refill and consumption are atomic across workers.
- [ ] Retry delay reflects time until the next token is available.
- [ ] Algorithm rollout cannot interpret old sliding-window keys as token-bucket state.
- [ ] Failure injection proves no accidental unlimited traffic during Redis errors or script failures.
- [ ] Comparative tests and measurements document burst shape, sustained rate, Redis operations, and storage tradeoffs.
- [ ] Existing throttled-state, concurrency, circuit-breaker, lease, and persistence invariants remain intact.

## Phase 1: Specify token-bucket semantics

### Step 1: Record the algorithm decision

- [ ] Add an ADR superseding the sliding-window portion of ADR 011 and updating ADR 004.
- [ ] Define refill rate, bucket capacity, fractional-token precision, initial bucket state, and idle expiration.
- [ ] Define the allowed burst after a long idle period and demonstrate how it differs from the old rolling-window guarantee.
- [ ] Define time authority and clock-skew handling for distributed workers.
- [ ] Define key versioning and mixed-version deployment behavior.
- **Verify:** examples and boundary tables are unambiguous for operators and tests.

### Step 2: Add algorithm contract tests

- [ ] Create implementation-neutral tests for empty bucket, partial refill, full refill, burst exhaustion, and retry delay.
- [ ] Add sustained-load tests proving average allowance converges to configured rate.
- [ ] Add per-subscription isolation and concurrent-worker tests.
- [ ] Add policy-change tests for rate and burst updates without stale state corruption.
- [ ] Avoid correctness tests based only on long wall-clock sleeps; isolate refill math or inject controlled time where practical.
- **Verify:** tests pass for the intended model and expose the old sliding-window semantic differences.

## Phase 2: Implement the distributed token bucket

### Step 3: Implement atomic Redis refill and consume

- [ ] Replace sorted-set operations with a versioned hash or compact value containing tokens and last-refill time.
- [ ] Use one Lua script for refill, capacity clamp, consume, TTL refresh, and retry-delay calculation.
- [ ] Use Redis server time or another explicitly justified time authority to avoid worker clock disagreement.
- [ ] Store fractional tokens with bounded precision and test rounding at low and high rates.
- [ ] Set idle TTL long enough to preserve expected burst state but finite enough to reclaim inactive-subscription keys.
- **Verify:** Redis Testcontainers tests cover atomicity, concurrency, expiration, and script errors.

### Step 4: Align in-memory fallback semantics

- [ ] Configure `golang.org/x/time/rate` from the same normalized policy.
- [ ] Match initial burst and retry-delay semantics as closely as the library permits.
- [ ] Preserve explicit degraded-mode observability from v0.9.0.
- [ ] Document that independent fallback buckets are not a globally coordinated limit.
- **Verify:** shared behavior tests run against Redis and in-memory implementations.

### Step 5: Roll out without key ambiguity

- [ ] Introduce a new key namespace such as `ratelimit:v2:{subscription_id}`.
- [ ] Do not migrate individual request timestamps into token state; initialize v2 according to the recorded rollout policy.
- [ ] Define safe behavior during mixed worker versions and prevent simultaneous old/new enforcement from producing an undocumented effective rate.
- [ ] Remove old sliding-window keys only after compatibility is no longer required, preferably by TTL rather than a blocking scan.
- **Verify:** a mixed-version simulation or compatibility test demonstrates the selected deployment sequence.

## Phase 3: Measure and document the tradeoff

### Step 6: Compare algorithms under representative load

- [ ] Build a controlled benchmark for one hot subscription and many moderately active subscriptions.
- [ ] Compare Redis command/script latency, memory per active subscription, accepted burst shape, and sustained throughput.
- [ ] Include rejection/retry-backlog effects, not only limiter microbenchmarks.
- [ ] Record environment and methodology; avoid universal throughput claims.
- **Verify:** repeated measurements support or challenge the migration rationale.

### Step 7: Update observability and documentation

- [ ] Update limiter metrics to expose allowed, throttled, degraded, and retry-delay behavior without subscription-cardinality explosion.
- [ ] Update dashboards and alerts for sustained throttling and degraded local enforcement.
- [ ] Update spec, architecture, README, limitations, ADRs, and `internal/resilience/README.md`.
- [ ] Add a learning note comparing strict rolling limits with rate-plus-burst contracts.
- **Verify:** all durable docs identify token bucket as current Redis and fallback behavior.

## Closure

- [ ] Lint, build, race-gated tests, Redis/PostgreSQL integration, E2E, and rate-oriented load validation pass.
- [ ] `PROGRESS.md` records measured behavior, rollout constraints, and remaining limits.
- [ ] Move this file to `done/` and return to feature selection in `docs/next-steps.md`.
