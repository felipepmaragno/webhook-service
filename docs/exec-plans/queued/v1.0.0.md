# Execution Plan: v1.0.0 Release Hardening

> **Status:** Queued for review
> **Estimated effort:** 1-2 focused engineering sessions
> **Depends on:** v0.14.0 minimal operational readiness
> **Release criterion:** Demonstrate and publish the final v1 state without adding product features.

## Goal

Finish Dispatch v1 by auditing the release gate, running the complete validation matrix, reconciling
the documentation set, and recording the final accepted boundaries.

This is not a feature increment. It exists to prove that the existing system satisfies the accepted
v1 promise or to identify a small release blocker that must be fixed before tagging v1.

## Accepted Contract

- No new product features.
- No broad refactors unless a release-gate defect requires them.
- No API contract hardening beyond a release blocker found during the audit.
- No package extraction from `internal/kafka`.
- No destination model redesign.
- No auth, multi-tenancy, UI, batching, ordering, transformations, or managed-service work.
- Release notes must be honest about accepted limitations and deferred work.
- The v1 release gate in `docs/v1-roadmap.md` is the authority for completion.

## Non-goals

- Do not implement queued `api-contract-hardening.md`.
- Do not implement the internal package-boundaries spike.
- Do not run a large capacity campaign beyond existing smoke/baseline evidence.
- Do not add a full backup/restore automation program.
- Do not add cloud-provider-specific deployment docs.

## Phase 1: Release Gate Audit

- [ ] Review every unchecked item in `docs/v1-roadmap.md`.
- [ ] For each item, classify it as:
  - satisfied by existing evidence;
  - accepted limitation;
  - deferred post-v1 work;
  - release blocker requiring a small fix.
- [ ] Update the roadmap checklist only when evidence is linked or the limitation is explicitly
  accepted.
- [ ] Do not convert deferred future work into v1 scope.
- **Verify:** the release gate has no ambiguous unchecked item at the end of the increment.

## Phase 2: Complete Validation Matrix

- [ ] Run build validation.
- [ ] Run full Go test suite.
- [ ] Run race-gated unit/component package suite.
- [ ] Run lint.
- [ ] Run `make validate-basic`.
- [ ] Render Compose files.
- [ ] Parse Kubernetes YAML.
- [ ] Validate relative Markdown links.
- [ ] Run `git diff --check`.
- [ ] Refresh coverage evidence if useful for release notes; do not chase arbitrary coverage targets.
- **Verify:** `PROGRESS.md` records exact commands and results.

## Phase 3: Documentation Reconciliation

- [ ] Reconcile README, product, spec, architecture, limitations, operations guide, v1 roadmap,
  next steps, ADR status notes, package READMEs, and progress.
- [ ] Remove stale references to superseded behavior where they describe current state rather than
  historical decisions.
- [ ] Keep historical ADRs and learnings intact when they are clearly historical.
- [ ] Ensure docs agree on:
  - single trusted environment;
  - at-least-once delivery;
  - per-subscription delivery identity;
  - subscription-scoped `max_delivery_rate`;
  - Redis requirement for distributed rate enforcement;
  - no application auth or multi-tenancy in v1;
  - no new planned feature work after v1.
- **Verify:** current-state docs do not contradict the v1 release boundary.

## Phase 4: Final V1 Summary

- [ ] Add concise release notes or a v1 summary document.
- [ ] Summarize:
  - what Dispatch is;
  - how to validate it locally;
  - what it guarantees;
  - what it intentionally does not guarantee;
  - accepted operational and security boundaries;
  - deferred post-v1 ideas.
- [ ] Link the summary from README and `PROGRESS.md`.
- **Verify:** a new reviewer can understand the final v1 state without reading every exec plan.

## Phase 5: Defer Remaining Technical Debt Explicitly

- [ ] Confirm `api-contract-hardening.md` remains queued and unversioned.
- [ ] Confirm `docs/spikes/internal-package-boundaries.md` remains a spike, not active work.
- [ ] Confirm destination-resource modeling, richer rate algorithms, auth, multi-tenancy, and
  Kafka outcome topics remain deferred.
- [ ] Update `docs/next-steps.md` so post-v1 work is clearly optional future direction, not the next
  required increment.
- **Verify:** no deferred item is presented as necessary for v1 completion.

## Phase 6: Release Closure

- [ ] Move this exec plan to `done/`.
- [ ] Update `PROGRESS.md` to state v1.0.0 is complete if the release gate passes.
- [ ] Update `docs/v1-roadmap.md` to mark v1.0.0 complete only when all release-gate outcomes are
  resolved.
- [ ] Leave the working tree clean and push the branch for review.
- **Verify:** the final state has one clear next action: review/tag the v1 release, not continue
  building features.
