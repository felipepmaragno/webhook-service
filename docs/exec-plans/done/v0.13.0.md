# Execution Plan: v0.13.0 - Terminal Replay and Retention

> **Status:** Complete
> **Target:** Replay failed deliveries without rewriting history and bound persisted delivery data without deleting active work.
> **Depends on:** v0.11.0 per-delivery runtime ownership and v0.12.0 receiver security
> **Followed by:** v0.14.0 operational readiness and measured capacity

## Goal

Give operators a supported way to retry a terminal failed destination and give the service a
bounded, observable storage lifecycle for attempt bodies and terminal delivery history.

Replay must preserve one authoritative runtime model. It schedules a new generation through the
existing delivery retry path; it does not call the delivery engine from the API, create another
queue, rewrite successful destinations, or erase prior attempts.

## Accepted Replay Contract

- Only a `failed` delivery is replayable. A delivered, pending, processing, retrying, or throttled
  delivery returns a conflict and is not mutated.
- `POST /deliveries/{id}/replay` atomically increments the delivery generation, resets that
  generation's attempt budget to zero, clears terminal/lease fields, and schedules it immediately
  as `retrying`.
- The stable delivery ID and frozen destination configuration do not change.
- Every attempt records the generation that produced it. Existing deliveries and attempts are
  generation `1`; the first replay creates generation `2`.
- Attempt numbers restart within each generation. Historical attempts are never updated or deleted
  by replay.
- The event projection is refreshed in the same transaction as replay scheduling.
- Concurrent replay requests are serialized by the terminal-state predicate: one succeeds and
  later requests observe a non-terminal delivery conflict.
- A successful response is `202 Accepted` and means durable retry scheduling, not receiver success.
- The API has no application authorization; replay remains protected by the deployment trust
  boundary documented for v1.

## Accepted Clean-Slate Policy

- No deployed database or supported old-schema consumer requires backward compatibility.
- The migration directory contains one current-state fresh-installation baseline.
- Delivery rows are the only processing, retry, lease, and replay ownership model.
- Every attempt has mandatory, matching event/delivery/subscription attribution.
- Transitional aggregate execution, event-level leases, direct event writes, batching, aliases,
  branches, tests, and current-state documentation are removed.
- Historical ADRs, plans, and learnings preserve the migration reasoning without keeping it live.

## Accepted Retention Contract

- Attempt response bodies are redacted after `ATTEMPT_BODY_RETENTION` while attempt metadata,
  status, error, duration, generation, and attribution remain.
- Terminal events and their cascading deliveries/attempts are deleted after `EVENT_RETENTION` only
  when no delivery is pending, processing, retrying, or throttled.
- Cleanup runs in bounded batches from the worker process. Multiple workers coordinate through
  PostgreSQL row locking with `SKIP LOCKED`; no singleton scheduler is required.
- Each cycle redacts attempt bodies before deleting terminal events.
- Defaults are 7 days for attempt bodies, 30 days for terminal events, a 1-hour interval, and 1,000
  rows per operation.
- Retention durations and interval must be positive, event retention must not be shorter than body
  retention, and batch size must be positive.
- Cleanup failure is logged and counted but does not stop delivery or retry processing.
- Shutdown waits for an in-flight cleanup cycle.

## Package Ownership Decision

The proposed `internal/delivery` extraction is not part of v0.13. Replay schedules normal retry work
through PostgreSQL and does not become a direct caller of `kafka.DeliveryHandler`, so the spike's
promotion trigger is absent. Keep the spike as a concluded/deferred architectural option and avoid
mixing package movement with replay state changes.

## Non-goals

- Replaying delivered or currently active destinations.
- Replaying an entire event or every destination in one API call.
- Archival storage, legal holds, tenant-specific retention, or a UI.
- A new Kafka replay topic, dead-letter queue, or separate cleanup service.
- General API hardening or the transport-independent delivery package extraction.

## Acceptance Criteria

- [x] A failed delivery can be durably scheduled as exactly one new generation through the API.
- [x] Replay preserves delivery identity, frozen destination data, and all prior attempts.
- [x] New attempts identify their replay generation and restart attempt numbering within it.
- [x] Concurrent, repeated, missing, and non-failed replay requests have deterministic behavior.
- [x] Replay uses the normal retry claim, lease, resilience, signing, persistence, and projection path.
- [x] The fresh baseline contains no aggregate execution compatibility or unattributed attempts.
- [x] Attempt bodies are redacted in bounded batches without deleting attempt metadata.
- [x] Terminal event cleanup cascades only after all deliveries are terminal and never deletes
  active/retryable work.
- [x] Cleanup scheduling, failures, redactions, deletions, and last-success time are observable.
- [x] Worker shutdown waits for cleanup and existing delivery/retry shutdown guarantees remain intact.
- [x] Documentation defines replay duplicate semantics, retention defaults, configuration, migration
  constraints, and operator responsibilities.
