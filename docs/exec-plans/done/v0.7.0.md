# Execution Plan: v0.7.0 — Retry claim leases and crash recovery

> **Status:** Done
> **Started:** 2026-06-12
> **Target:** Recover abandoned retry claims safely without allowing stale workers to overwrite newer outcomes.
> **Depends on:** v0.6.0 atomic delivery persistence and Kafka commit safety
> **Followed by:** queued v0.8.0 poller throughput and observability

## Goal

Replace permanent `processing` claims with expiring, owner-fenced leases so retry
events survive worker crashes while retaining at-least-once delivery semantics.

## Acceptance criteria

- [x] Every retry claim records an owner and expiration deadline atomically with the transition to `processing`.
- [x] Expired `processing` events become claimable again without manual database intervention.
- [x] A stale worker cannot persist an outcome after another worker has reclaimed the event.
- [x] Successful, retrying, throttled, and failed outcomes clear lease metadata atomically with state persistence.
- [x] Concurrent workers do not hold valid claims for the same event simultaneously.
- [x] Schema migration is backward-safe for existing rows and reversible through its down migration.
- [x] Lint, build, integration tests, and E2E crash-recovery coverage pass.

## Phase 1: Define and migrate the lease model

### Step 1: Record the architecture decision

- [x] Add or supersede an ADR defining PostgreSQL polling as the retry scheduler and expiring owner-fenced claims as its crash-recovery mechanism.
- [x] Define the lease duration default, ownership identity, expiration behavior, and at-least-once duplicate-delivery tradeoff.
- [x] Keep PostgreSQL as the only durable retry schedule; do not add Redis or Kafka retry topics.
- **Verify:** ADR agrees with the living spec and existing Kafka/PostgreSQL responsibility split.

### Step 2: Add lease state to persistence and domain models

- [x] Add nullable `processing_owner` and `processing_deadline` columns plus an index supporting expired-lease lookup.
- [x] Extend the event persistence model and scans to carry lease metadata where required.
- [x] Configure a worker lease duration with a documented default longer than the maximum normal delivery timeout for one claimed batch.
- [x] Use the existing worker `InstanceID` as the claim owner.
- **Verify:** migration up/down tests and configuration tests pass.

## Phase 2: Implement owner-fenced claiming

### Step 3: Replace pending fetch with an explicit claim operation

- [x] Rename the repository operation to express claiming rather than reading.
- [x] Atomically claim due `retrying`/`throttled` events and expired `processing` events using `FOR UPDATE SKIP LOCKED`.
- [x] Set `status=processing`, owner, and deadline in the same statement.
- [x] Return whether each event was newly due or reclaimed for observability.
- **Verify:** PostgreSQL integration tests cover eligibility, limits, owner fields, and future deadlines.

### Step 4: Fence outcome persistence by lease owner

- [x] Require retry-originated outcome persistence to match event ID, `status=processing`, owner, and exact deadline.
- [x] Treat zero updated rows as a lost/stale claim, not as successful persistence.
- [x] Clear lease fields in the same transaction that writes the outcome and attempts.
- [x] Ensure an expired first worker cannot overwrite a later lease generation's committed result.
- **Verify:** concurrent repository tests exercise reclaim and stale-owner rejection deterministically.

## Phase 3: Crash recovery behavior

### Step 5: Wire worker identity and lease configuration

- [x] Pass `InstanceID` and lease duration from worker configuration into the retry poller claim operation.
- [x] Log claim owner, lease deadline, and reclaimed count without high-cardinality event labels in metrics.
- [x] Preserve graceful shutdown; do not release claims by resetting rows during shutdown because in-flight HTTP outcomes may be uncertain.
- **Verify:** worker bootstrap and poller unit tests pass.

### Step 6: Add crash and expiration scenarios

- [x] Prove a claimed event is unavailable to a second worker before expiration.
- [x] Prove it becomes claimable after expiration.
- [x] Prove the stale first lease cannot commit after reclamation.
- [x] Add a thin E2E recovery scenario that abandons a claim and reaches a valid final state after lease expiry.
- **Verify:** integration and E2E suites pass repeatedly without arbitrary long sleeps.

### Step 7: Update durable documentation

- [x] Update the living spec state machine with lease acquisition, expiration, and reclaim behavior.
- [x] Update architecture diagrams and database schema documentation.
- [x] Update limitations and operational guidance for duplicate delivery after lease expiry.
- [x] Add a learning note about leases, fencing tokens/owners, and why timeout alone is insufficient.
- **Verify:** docs consistently distinguish row locking from a durable processing lease.
