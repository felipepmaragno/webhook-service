# Execution Plan: v0.11.0 - Per-Subscription Delivery Processing

> **Status:** Done
> **Target:** Make per-delivery state authoritative for initial processing, retries, event projection, and operator queries.
> **Depends on:** v0.10.0 per-subscription delivery persistence
> **Followed by:** v0.12.0 cryptographic signatures and deployment security contract

## Goal

Cut runtime ownership over from aggregate event processing to independent deliveries so
one destination's failure no longer repeats or obscures another destination's outcome.

## Acceptance criteria

- [x] A Kafka event initializes its frozen delivery set durably before external calls.
- [x] Duplicate Kafka processing reuses that set and skips already complete deliveries.
- [x] Every HTTP attempt is attributed to one delivery and subscription.
- [x] Retry claims and leases belong to deliveries and preserve owner/deadline fencing.
- [x] Mixed destination outcomes remain independently inspectable and retryable.
- [x] Event status is derived from delivery states using the v0.10.0 projection contract.
- [x] New events no longer use event-level retry ownership as authoritative state.
- [x] Existing pre-cutover events remain readable and have a documented recovery policy.

## Phase 1: Initial delivery cutover

### Step 1: Specify initialization and duplicate behavior

- [x] Add tests proving the first Kafka handling freezes matching subscriptions.
- [x] Add tests proving later subscription changes do not alter the target set.
- [x] Add tests proving Kafka redelivery does not call already delivered or terminal destinations.
- [x] Define no-subscription completion behavior.
- **Verify:** tests fail against aggregate fan-out processing.

### Step 2: Initialize before side effects

- [x] Persist the event and delivery set before making HTTP calls.
- [x] Claim processable deliveries with an ownership boundary that survives worker failure.
- [x] Process only deliveries that are not already complete or currently owned.
- [x] Commit Kafka offsets only after every selected delivery has a durable state or retry schedule.
- **Verify:** failure injection covers crashes before calls, after calls, during persistence, and before offset commit.

## Phase 2: Independent outcomes and retries

### Step 3: Refactor delivery execution

- [x] Deliver one event-subscription pair as the unit of work.
- [x] Apply rate, circuit, and concurrency policy to that delivery's destination.
- [x] Persist the delivery transition and attempt atomically.
- [x] Remove worst-outcome-wins as the retry ownership rule; retain only event projection.
- **Verify:** mixed fan-out tests prove successful destinations are not repeated because another destination retries.

### Step 4: Move retry claims to deliveries

- [x] Claim due and expired delivery rows with owner/deadline fencing.
- [x] Update the retry poller and processor contracts to operate on deliveries.
- [x] Preserve bounded concurrency and observability from v0.8.0.
- [x] Reject stale delivery outcomes without rolling back unrelated delivery outcomes in the same scheduler cycle.
- **Verify:** PostgreSQL integration and race tests cover concurrent claims, expiration, stale writers, and partial mixed batches.

## Phase 3: Queries and legacy boundary

### Step 5: Make delivery reads authoritative

- [x] Return per-delivery status and attempts through the supported operator API.
- [x] Derive event status consistently from persisted delivery rows.
- [x] Keep existing event lookup behavior compatible where possible and document any versioned response change.
- [x] Define how legacy aggregate retry rows are drained, migrated, or kept on the old path until terminal.
- **Verify:** API and E2E tests cover single destination, fan-out, no destination, retries, throttling, and legacy reads.

### Step 6: Remove obsolete runtime ownership

- [x] Remove event-level claim/write paths that are no longer used for new events.
- [x] Keep migration compatibility code isolated and explicitly temporary where needed.
- [x] Update spec, architecture, ADRs, README, limitations, package READMEs, dashboards, and runbooks.
- [x] Add a learning note about state ownership and external side-effect idempotency.
- **Verify:** searches and tests show one authoritative processing model for new events.
