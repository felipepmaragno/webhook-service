# Execution Plan: v0.12.0 - Receiver and Deployment Security

> **Status:** Done
> **Target:** Replace the signature placeholder with a verifiable cryptographic contract and make the supported API trust boundary explicit.
> **Depends on:** v0.11.0 per-delivery processing and the post-v0.11 simplification pass
> **Followed by:** v0.13.0 terminal-delivery replay, retention, and cleanup

## Goal

Let webhook receivers verify that a request was produced by Dispatch while preventing
known secret disclosure through the API and documenting the security boundary operators
must provide around a self-hosted deployment.

This increment closes the v1 receiver-authenticity criterion. It does not turn Dispatch
into a public or multi-tenant service. API authentication, TLS termination, network
restriction, and secret-manager integration remain deployment responsibilities for the
accepted single-trust-domain product.

## Accepted Signature Contract

The implementation must follow one documented v1 contract:

- `X-Dispatch-Timestamp` contains Unix time in decimal seconds.
- `X-Dispatch-Signature` contains `v1=<lowercase hexadecimal digest>`.
- The signed bytes are the ASCII timestamp, one `.` byte, and the exact HTTP request body:
  `timestamp + "." + body`.
- The digest is HMAC-SHA256 using the subscription secret.
- Receivers verify the exact raw body before JSON parsing and compare digests with
  `hmac.Equal` or an equivalent constant-time operation.
- Receiver guidance uses a bounded timestamp tolerance to reduce replay exposure and
  deduplicates by event ID because signatures do not change at-least-once delivery.
- Requests without a configured secret omit both signature headers.
- The old `X-Signature: sha256=<payload-prefix>` placeholder is removed; it was explicitly
  documented as non-cryptographic and had no supported security compatibility guarantee.

## Accepted Rotation Contract

- A subscription has one active secret for newly initialized deliveries.
- Rotation replaces that active secret without returning either the old or new secret in
  an API response.
- Delivery rows retain their frozen secret. Deliveries initialized before rotation,
  including retries, continue signing with the old secret; deliveries initialized after
  rotation use the new secret.
- Operators must keep both secrets valid at the receiver until all deliveries frozen with
  the old secret are terminal or outside the accepted retention window.
- Rotation is an explicit operator action against an existing subscription; direct
  database edits are not the supported workflow.
- Secret-at-rest encryption and external secret-manager synchronization are not added in
  this increment. PostgreSQL and backup protection remain deployment obligations.

## Non-goals

- Application-level API authentication, authorization, RBAC, or tenant isolation.
- Exactly-once delivery or complete prevention of valid signed-request replay.
- Automatic secret-manager integration or application-level encryption of stored secrets.
- Destination ownership verification or a webhook challenge handshake.
- General API contract hardening beyond security-critical response DTOs and rotation input.
- TLS implementation inside Dispatch when a reverse proxy or private network owns TLS.

## Acceptance Criteria

- [x] Every webhook with a configured secret uses the documented timestamped HMAC-SHA256
  contract over the exact transmitted body.
- [x] Published language-independent test vectors reproduce the emitted timestamp,
  canonical signed bytes, and digest.
- [x] Receiver verification guidance covers raw-body handling, timestamp tolerance,
  constant-time comparison, multiple valid rotation secrets, and event-ID deduplication.
- [x] Subscription secrets are write-only: create, list, rotate, logs, metrics, errors,
  examples, and delivery-query responses never disclose them.
- [x] A supported rotation operation updates the secret used by future delivery
  initialization without changing already frozen deliveries.
- [x] Secret rotation has deterministic not-found, invalid-input, persistence-error, and
  success behavior with focused API and PostgreSQL tests.
- [x] The deployment contract states that API authentication, authorization, TLS, and
  network restriction are external responsibilities.
- [x] Compose and Kubernetes examples do not imply safe public exposure or commit usable
  production credentials.
- [x] Signature and security behavior are reflected consistently in product, spec,
  architecture, limitations, README, package context, and deployment documentation.
- [x] Existing delivery, retry, persistence, and at-least-once guarantees remain intact.

### Step 6: Add supported secret rotation

- [x] Add a consumer-owned repository operation that updates only the active subscription
