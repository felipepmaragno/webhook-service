# Execution Plan: v0.8.0 — Retry poller throughput and observability

> **Status:** Active
> **Started:** 2026-06-14
> **Target:** Drain retry backlogs predictably with bounded concurrency and production-grade visibility.
> **Depends on:** v0.7.0 retry claim leases and crash recovery
> **Followed by:** queued v0.9.0 rate-control normalization, then the per-subscription delivery model

## Goal

Make retry processing capacity explicit, bounded, measurable, and responsive to backlog
without weakening the transaction and lease invariants established in v0.6.0–v0.7.0.

## Acceptance criteria

- [x] `MaxConcurrentBatches` is enforced and no longer dead configuration.
- [x] The poller drains immediately available retry batches while capacity exists instead of waiting one full interval per batch.
- [x] Idle polling remains low-cost and configurable.
- [x] Shutdown stops new claims and waits for bounded in-flight batches.
- [x] Metrics expose retry backlog age, claimed/reclaimed counts, active batches, empty polls, and persistence/claim failures.
- [x] Load-oriented tests prove bounded concurrency and materially better backlog drain behavior.
- [x] Existing delivery rate limiting, circuit breaking, and per-subscription semaphore behavior remains intact.

## Phase 1: Define capacity and scheduling behavior

### Step 1: Specify poller invariants with tests

- [x] Add deterministic tests proving the configured maximum number of concurrent batches is never exceeded.
- [x] Add tests proving a full batch triggers another immediate claim while capacity remains.
- [x] Add tests proving an empty or partial batch returns the poller to interval-based waiting.
- [x] Add shutdown tests with in-flight processing and available backlog.
- **Verify:** tests fail against the current one-batch-per-tick implementation.

### Step 2: Implement bounded backlog draining

- [x] Introduce an internal capacity controller sized by `MaxConcurrentBatches`.
- [x] Claim new work only when a processing slot is available.
- [x] Continue claiming immediately after a full batch; stop draining after an empty or partial batch to avoid a busy loop.
- [x] Prevent overlapping ticker-triggered drain loops.
- [x] Keep batch size and poll interval independently configurable.
- **Verify:** poller unit tests and race detector pass.

## Phase 2: Operational visibility

### Step 3: Add retry scheduler metrics

- [x] Add counters for claimed events, reclaimed events, empty polls, claim failures, persistence failures, and stale-owner rejections.
- [x] Add gauges for active retry batches and currently leased events where collection is inexpensive.
- [x] Add a histogram or gauge for retry scheduling lag: claim time minus `next_attempt_at`.
- [x] Avoid event IDs and subscription IDs as labels on scheduler-level metrics.
- **Verify:** metrics registration tests and worker `/metrics` checks pass without duplicate collectors.

### Step 4: Add backlog queries and alerts

- [x] Add an efficient repository aggregate for due retry count, oldest due age, and expired processing count if metrics cannot derive them from claim results.
- [x] Ensure supporting indexes are justified with `EXPLAIN` against representative data.
- [x] Add Prometheus alert examples for growing retry lag, expired claims, and repeated persistence failures.
- [x] Update Grafana worker dashboards with retry backlog and lease health panels.
- **Verify:** queries use intended indexes and dashboard JSON remains valid.

## Phase 3: Performance validation and documentation

### Step 5: Validate backlog behavior

- [x] Add a controlled integration/load scenario with a seeded retry backlog and deterministic delivery endpoint.
- [x] Measure drain rate for the old default-equivalent configuration and the bounded concurrent configuration.
- [x] Verify database pool limits, semaphore limits, and destination rate limits remain the effective safety boundaries.
- [x] Record results as operational guidance, not universal throughput claims.
- **Verify:** repeated test runs show bounded concurrency and no stuck leases.

### Step 6: Update durable documentation

- [x] Update the living spec with scheduler capacity and observable guarantees, without embedding implementation checklists.
- [x] Update architecture and observability ADRs with poller control flow and metric meanings.
- [x] Update README operational commands, dashboard descriptions, limitations, and next steps.
- [x] Add a learning note covering backlog draining, backpressure, and why polling interval is not a throughput control.
- **Verify:** documentation distinguishes delivery capacity, claim capacity, and retry scheduling latency.

## Closure

- [x] Lint, build, race-gated tests, integration tests, E2E tests, and load-oriented retry validation pass.
- [x] `PROGRESS.md` records measured behavior, configuration defaults, and remaining scaling limits.
