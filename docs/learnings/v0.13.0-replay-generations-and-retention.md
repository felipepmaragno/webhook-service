# V0.13.0: Replay Generations and Bounded Retention

## Why replay is a new generation

A failed delivery is historical truth: it records which frozen destination was called, how many
attempts were consumed, and why processing stopped. Resetting that row without another identity
dimension would make old and new attempts appear to belong to one attempt budget.

Generation keeps the stable delivery identity while making each operator decision explicit. Replay
increments the generation, resets only the new generation's attempt count, and leaves prior attempts
unchanged. This is smaller than creating a second delivery row and more honest than rewriting history.

## Why the API schedules instead of delivers

The API transaction changes durable state from `failed` to immediately due `retrying`. It does not
call the receiver. The retry poller then applies the same claim lease, rate controls, circuit breaker,
signature generation, HTTP client, and outcome transaction used by ordinary retries.

This preserves one execution path and gives `202 Accepted` a precise meaning: scheduling committed.
It does not promise receiver success. A direct API-to-receiver call would duplicate delivery policy
and couple request latency to external systems.

## Read compatibility is not execution compatibility

Pre-delivery-model events can be read faithfully, but their original destination set was never
persisted. Keeping old aggregate retry methods could not reconstruct that missing attribution; it
only made unsupported work look executable. Migration 006 therefore marks unattributable active rows
failed and requires deliberate resubmission. Historical reads remain because they preserve evidence.

The engineering lesson is to separate the questions: "Can old data still be explained?" and "Can
old work still execute under today's invariants?" They often require different answers.

## Clean-slate correction

That distinction matters in deployed systems, but Dispatch has no deployed database. Retaining read
compatibility therefore protected a hypothetical consumer while increasing the active model's
complexity. Before commit, the project replaced the migration chain with one current-state baseline,
made attempt attribution mandatory, removed event-level leases, and deleted batching/direct-write
surfaces with no production caller. The migration discussion remains useful history, not a runtime
requirement.

## Why retention belongs in PostgreSQL coordination

Every worker may run cleanup. Bounded CTEs with `FOR UPDATE SKIP LOCKED` split eligible rows between
workers without leader election, another queue, or a singleton service. Body redaction runs before
event deletion so short-lived response data has the earliest cleanup opportunity.

Deletion eligibility is a persistence invariant, not scheduler logic. PostgreSQL excludes any event
with active delivery work in the same statement that locks deletion candidates. The scheduler only
owns timing, failure continuation, metrics, and graceful shutdown.

## Tradeoffs retained deliberately

- Replay remains at least once and can produce duplicate receiver calls.
- Retention permanently removes query and replay history; archival and legal holds are not supported.
- Cleanup is eventual and may process more slowly than data arrives; counts, duration, failures, and
  last success make that visible for v0.14 operational alerting.
- API authorization remains a deployment trust-boundary responsibility for the v1 single-organization model.
