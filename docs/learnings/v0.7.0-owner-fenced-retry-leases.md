# v0.7.0 - Owner-Fenced Retry Leases

## Row locking is not durable ownership

`FOR UPDATE SKIP LOCKED` coordinates transactions while their locks are held. Once the claim
transaction commits, the lock disappears. A `processing` status left behind is only data; without
an expiration rule, it can remain stuck forever after a worker crash.

A durable claim therefore needs persisted ownership and a deadline, not only a row lock.

## Expiration alone is unsafe

Suppose worker A claims an event and becomes slow. Its lease expires, worker B reclaims the event,
and both HTTP calls finish. If worker A can still update by event ID, it may overwrite worker B's
newer state. Expiration restores availability but creates a stale-writer race.

The write must be fenced by the lease generation observed during the claim.

## Why owner plus deadline is the fence

`INSTANCE_ID` identifies the worker, but it is not sufficient by itself. The same worker identity
can reclaim an event after expiration, especially across process restarts or misconfigured replicas.
Matching both owner and exact deadline distinguishes successive lease generations without adding a
separate token column.

The guarded update is conceptually:

```sql
UPDATE events
SET ..., processing_owner = NULL, processing_deadline = NULL
WHERE id = $1
  AND status = 'processing'
  AND processing_owner = $owner
  AND processing_deadline = $deadline;
```

Zero affected rows is a correctness signal, not a successful no-op. The outcome and attempts must
roll back and return `ErrClaimLost`.

## Lease duration tradeoff

A short lease recovers crashes quickly but increases duplicate delivery when legitimate work runs
long. A long lease reduces false expiry but delays crash recovery. The default 30 seconds is longer
than the normal 10-second HTTP timeout; production tuning should include connection behavior and
expected batch overhead.

## Migration lesson

Adding nullable lease columns is not enough. Existing `processing` rows would receive NULL metadata
and remain ineligible forever. The migration must deliberately convert legacy processing rows into
immediately expired claims so the new system can recover old state.

## Engineering takeaway

Leases provide liveness; fencing provides safety. A crash-recovery design needs both, and integration
tests must prove expiration, concurrency, stale rejection, transaction rollback, and upgrade behavior
against the real database.
