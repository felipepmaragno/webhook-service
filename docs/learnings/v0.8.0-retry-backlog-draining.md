# Retry Backlog Draining and Backpressure

## The original mistake

The retry poller had a `MaxConcurrentBatches` field, but every timer tick simply claimed
one batch and launched a goroutine. The field was dead configuration, full backlogs waited
one interval between claims, and slow batches could overlap across ticks without a real
bound.

This mixed two different controls:

- **discovery latency:** how long an idle scheduler waits before checking for newly due work;
- **processing capacity:** how much already-due work a worker may process concurrently.

Using the polling interval as an accidental throughput control makes recovery slow when
the interval is large and creates overlap risk when it is small.

## The scheduler model

One coordinator owns claims for each worker:

1. Start a drain cycle on startup or interval tick.
2. Claim only when a batch-processing slot is available.
3. If a claim is full, keep draining immediately while capacity exists.
4. If a claim is partial or empty, treat that as exhaustion and return to interval waiting.
5. When a batch finishes, release its slot and continue only if the current drain cycle is
   still active.
6. On shutdown, stop new claims and wait for tracked work.

The single coordinator also prevents overlapping ticker-triggered drain loops.

## Why partial means stop

A full claim is evidence that more due work may exist beyond the query limit. A partial
claim is evidence that the query saw less work than it could take. Immediately polling
again after a partial or empty result would create a busy loop against PostgreSQL.

This is a heuristic based on the repository contract. If future claim filtering can hide
eligible work, that assumption must be revisited explicitly.

## Backpressure layers

`RETRY_MAX_CONCURRENT_BATCHES` is only the outer scheduler bound. Effective capacity is
also constrained by:

- batch size;
- PostgreSQL connection pool and transaction latency;
- per-subscription distributed semaphore;
- receiver rate limits and circuit breakers;
- HTTP timeout and destination latency;
- event fan-out and worker CPU/memory.

Increasing scheduler concurrency without checking these layers can move backlog into the
database pool or receiver rather than improving recovery.

## Observability lesson

Throughput counters alone cannot show whether retry work is healthy. The useful signals
are:

- due count and oldest due age;
- expired and active leases;
- active processing batches;
- eligibility-to-claim scheduling lag;
- claim and persistence failures;
- reclaimed work and stale-owner rejection.

Scheduler metrics intentionally avoid event and subscription labels. Those identities
would create high-cardinality time series without improving scheduler-level decisions.

## Controlled result

With 20 batches, five events per batch, and a synthetic two-millisecond processor, four
batch slots drained the backlog in about 11.2 ms versus 44.3 ms with one slot. The near
4x result validates the coordinator under parallel work; it does not predict production
delivery throughput.

## Engineering takeaway

Polling frequency, claim capacity, and delivery capacity are separate concepts. Name and
measure them separately. A scheduler should be eager while known work exists, quiet when
idle, and bounded at every downstream resource.
