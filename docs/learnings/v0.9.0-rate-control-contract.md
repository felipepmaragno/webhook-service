# v0.9.0: Rate-Control Contract Normalization

## Lesson

One configuration field should not represent multiple resource controls. `rate_limit` looked simple,
but the system used it as requests per second, semaphore capacity, and an implied Redis default.
Those are different dimensions:

- **Rate** controls how many requests start over time.
- **Burst** controls how much short-term spike capacity an algorithm can spend immediately.
- **Concurrency** controls how many HTTP calls can be in flight at the same time.

Coupling them made the system hard to reason about. Increasing `rate_limit` to allow more
throughput could also increase simultaneous receiver pressure. Lowering it to protect a receiver
could also reduce concurrency even when the receiver mostly needed smoother pacing.

## Design Takeaway

Normalize contracts before swapping algorithms. Moving directly to a distributed token bucket would
have mixed two problems:

1. What does the product/API promise?
2. Which algorithm best enforces that promise?

v0.9 solves the first problem while intentionally keeping the Redis sliding-window log. This makes
a future token-bucket spike smaller and easier to judge with measurements.

## Backpressure State

Pre-HTTP rejections are not delivery failures:

- rate-limited;
- circuit open;
- semaphore full.

No HTTP request happened, so no delivery attempt should be recorded and the event attempt count
should not advance. Persisting these as `throttled` keeps the state model honest and protects retry
budget for real receiver attempts.

## Operational Tradeoff

Redis fallback preserves liveness but weakens the global guarantee. When Redis is down, each worker
uses a local limiter. With `N` active workers, the system can temporarily exceed the configured
global rate by roughly `N`. That is acceptable for this project because v1 favors understandable
recovery over fail-closed receiver protection, but it must be visible in metrics and logs.

## Practical Guidance

When adding a new control, ask:

- What physical resource does this control protect?
- What are its units?
- Is it per subscription, per worker, per tenant, or global?
- What happens when distributed coordination is unavailable?
- Does rejection happen before or after an HTTP attempt?

Answering those questions in the contract first keeps implementation choices from leaking into
the product model.
