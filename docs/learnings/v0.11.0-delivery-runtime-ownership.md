# v0.11.0: State Ownership Must Match the Side Effect

The important engineering lesson in v0.11 is that the durable state owner must be the same unit
that performs the external side effect.

The old model let one aggregate event own many webhook calls. That was simple, but it created
bad recovery semantics:

- one destination failure could repeat another destination that already succeeded;
- retry ownership could not target only the failing destination;
- attempt history could not reliably answer "which subscription received this call?";
- later subscription changes could affect retry behavior for an older event.

The fix was not just adding a `deliveries` table. The runtime had to move to that table:

1. freeze the destination set before HTTP calls;
2. claim delivery rows before processing;
3. perform one webhook side effect for one delivery;
4. persist the delivery outcome and attributed attempt atomically;
5. project event status from delivery rows.

The subtle tradeoff is visible after a persistence failure. If the HTTP call happened but the
outcome transaction failed, the system cannot honestly record the attempt. Instead, it preserves
recovery through the delivery lease. Kafka redelivery reuses the frozen delivery set and avoids
immediate duplicate calls while the lease is active; after lease expiry, the retry poller can recover.

That is not exactly-once delivery. It is a clearer at-least-once boundary: duplicates are still
possible, but the unit that can duplicate is now the exact destination that still lacks a durable
terminal outcome.
