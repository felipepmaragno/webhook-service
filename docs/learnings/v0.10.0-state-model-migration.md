# v0.10.0: Changing a State Model in Two Increments

## Lesson

Changing the ownership unit of a system is riskier than adding a table. Dispatch is moving from
aggregate event state to per-subscription delivery state. If schema, repository behavior, worker
processing, retry ownership, and API semantics all changed in one increment, any bug would be hard
to isolate.

The safer move is a two-step migration:

1. Add the durable model and compatibility reads.
2. Cut runtime processing over after the model is validated.

v0.10 implements the first step. v0.11 will implement the second.

## Why This Matters

The old aggregate event model caused accidental complexity:

- one destination could make the whole event terminal;
- retrying one destination could repeat calls to destinations that already succeeded;
- attempts could not always be attributed to a subscription;
- subscription changes could affect future retry cycles.

The new delivery model fixes the domain boundary, but activating it too early would risk Kafka
commit safety, retry lease fencing, and attempt history.

## Practical Guidance

When changing a state model in a reliable system:

- introduce the new durable representation before depending on it;
- make the migration reversible while the old runtime path is still active;
- keep legacy reads explicit instead of inventing historical data;
- test projection rules as pure domain behavior;
- cut over processing only after schema and repositories are boring.

Good state migrations reduce uncertainty. They do not hide it.
