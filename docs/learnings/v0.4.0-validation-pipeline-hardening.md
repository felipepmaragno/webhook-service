# v0.4.0 — Validation Pipeline Hardening

## Why this increment mattered

The project already had good unit and component coverage in some areas, but the
automated validation pipeline was weaker than the harness claimed. In practice:

- CI did not enforce all of the documented baseline
- Redis-backed tests still depended on host-local conventions
- there was no automated system-level guard rail for API → Kafka → worker → retry flow

The goal of this increment was not just "more tests". The goal was to improve the
trustworthiness of change.

## Main lessons

### 1. A thin E2E layer is worth more than a broad flaky one

For this project, the right end-to-end strategy is:

- few scenarios
- real dependencies
- deterministic assertions
- high-value contract coverage

The implemented smoke layer covers:

- happy path delivery
- retry path with failure then recovery

That was enough to catch a real persistence bug that lower-level tests did not expose.

### 2. Shared business logic does not imply shared persistence semantics

The most important bug found in this increment was in the retry path.

#### Root cause

Fresh Kafka events and retry-polled DB events were both going through the same
delivery logic and then using the same persistence path.

That was wrong.

- Kafka-originated events may need a new outcome row written
- retry-polled events already exist in the database and must be updated

The old retry path reused `CreateBatch`, which eventually hit `INSERT ... ON CONFLICT DO NOTHING`.
That meant a retried event could be successfully delivered and still remain stuck in
`processing` in the database.

#### Fix

Split the handler into:

- shared outcome computation
- source-specific persistence

Concretely:

- `processBatchResults` computes delivery outcomes
- `ProcessBatch` persists Kafka-originated events with create semantics
- `ProcessEvents` persists retry-polled events with update semantics

#### Engineering takeaway

If two flows share logic but not state ownership, share the computation and separate
the persistence step.

### 3. Startup code should be reusable if you want serious system tests

Before this increment, service wiring lived mainly inside `cmd/*`.

That is fine for production entrypoints, but poor for automation. If startup only lives
in `main`, tests usually drift toward:

- shelling out to binaries
- shelling out to `docker compose`
- duplicating startup logic

The refactor into reusable internal bootstrap code made it possible to:

- start real services in-process for tests
- reuse production wiring instead of reimplementing it
- keep `cmd/*` thin

This is not abstraction for aesthetics. It is a testability and maintainability boundary.

### 4. Infrastructure-backed tests should own their dependencies

Redis tests that assume `localhost:6379` are weaker than tests that start Redis themselves.

Reasons:

- machine state leaks into the result
- CI and local behavior diverge
- failures become harder to diagnose

Using Testcontainers makes the dependency lifecycle part of the test harness, which is
exactly what a strong CI baseline needs.

### 5. Good E2E tests can reveal better architecture

The retry persistence bug forced a refactor in `internal/kafka/handler.go`.

This is the pattern to notice:

- test exposes a real inconsistency
- fix changes both correctness and structure
- the system becomes easier to reason about afterward

That is a strong signal that the test added real design value, not just coverage.

## Practical advice for future work

### When touching `internal/kafka/handler.go`

Always ask:

- is this event coming from Kafka or from the retry poller?
- should the outcome create a row or update a row?
- is the delivery logic being changed, or only the persistence semantics?

If that distinction gets blurred again, the same class of bug can return.

### When adding new automated validation

Prefer this order:

1. unit/component tests
2. infra-backed integration tests
3. thin E2E smoke
4. heavier compose/demo/load checks outside the PR gate

That keeps the pipeline useful instead of slow and noisy.

### When refactoring startup or orchestration code

If the code is hard to run in-process, it is usually also hard to test and hard to evolve.
That is often a sign the composition boundary needs improvement.

## Known tradeoff kept intentionally

The E2E smoke test uses:

- real PostgreSQL
- real Redis
- real Kafka
- real API
- real delivery handler
- real retry poller

But it uses a deterministic direct Kafka partition reader in the smoke harness rather than
consumer-group coordination.

Reason:

- consumer-group coordination is more operationally realistic
- but it was too unstable for a thin PR-gated smoke layer

So the current choice optimizes for deterministic regression detection. Consumer-group
behavior remains a separate gap to close later if needed.

## Mentor note

The core lesson from this increment is that quality systems are built around explicit
boundaries:

- boundary between computation and persistence
- boundary between app startup and process entrypoints
- boundary between fast tests and expensive tests
- boundary between documented intent and mechanically verified reality

That is what makes a codebase easier to change without losing control.
